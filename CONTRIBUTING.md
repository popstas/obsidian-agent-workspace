# Как дорабатывать Agent Workspace

Этот файл — про разработку самой базы. Если ты развернул vault для себя, он тебе не нужен: скилл `demo-content-delete` предложит его удалить.

## Анатомия репозитория

Репозиторий — это три вещи одновременно, и путать их не стоит:

- **Плагин для трёх агентов.** `.claude-plugin/`, `.codex-plugin/` и `.cursor-plugin/` —
  три манифеста, указывающие на один и тот же каталог `skills/`. Часть полей в них
  дублируется намеренно: `version` держится одинаковой во всех пяти файлах
  (`scripts/lib/repo.mjs`, список `VERSION_FILES`), а `.claude-plugin/marketplace.json`
  обязан ссылаться на имя и версию из `.claude-plugin/plugin.json`. И то, и другое
  проверяет `tests/manifests.test.mjs` — руками сверять не нужно.
- **Готовое рабочее пространство.** Корневые `tasks.md`, `projects.md`, `Log/`, `Notes/`,
  `.obsidian/` — не примеры в документации, а файлы, которые пользователь получает клоном
  и начинает править с первого дня.
- **Источник демо-контента.** `demo-manifest.json` описывает, что скилл
  `demo-content-delete` убирает после адаптации, тремя списками: `demoFiles` — примеры
  логов, отчётов и заметок; `setupDocs` — `README.md`, `README_ru.md`, `INTEGRATION.md`
  и этот файл; `baseOnly` — то, что нужно только разработке базы (`tests`, `.github`,
  `package.json`, `CHANGELOG.md`, генераторы). Файлы в первых двух списках пинятся по
  sha256, поэтому после любой правки README, `INTEGRATION.md` или `CONTRIBUTING.md`
  нужно `npm run gen:demo-manifest`, иначе тест целостности покраснеет.

Отдельного реестра плагинов у проекта нет: маркетплейс живёт в самом репозитории
(`.claude-plugin/marketplace.json`), и пользователь подключает его как
`popstas/obsidian-agent-workspace`. Переименование репозитория меняет и имя маркетплейса,
и имя плагина — уже установленные копии после этого нужно переставлять.

## Разовая настройка

```bash
git config core.hooksPath .githooks
```

Хук `pre-commit` пересобирает `skills/Skills list.md`, когда меняется любой `SKILL.md`, и запускает `npm test` (включая guard приватности) — коммит с красным тестом не пройдёт. Хуки не переживают `clone`, поэтому настоящая гарантия — проверка в CI: она регенерирует список и гоняет те же тесты, падая, если что-то разошлось.

Проверить, что хук включён: `git config core.hooksPath` должен вывести `.githooks`. Пустой вывод значит, что хук не работает и красный тест ты увидишь только в CI. Так уже было дважды: правка `CONTRIBUTING.md` без пересборки демо-манифеста и новый скилл без обновления списков.

## Что пересобрать после правки

Часть файлов сгенерирована или закреплена тестами. Если поправить исходник и не обновить производное, CI покраснеет. Перед коммитом сверься с таблицей:

| Что меняешь | Что сделать |
|---|---|
| Добавляешь, удаляешь или переименовываешь скилл в `skills/` | Обновить эталонный список `EXPECTED` в `tests/skills.test.mjs` (по алфавиту). Запустить `npm run gen:skills-list`. Дописать скилл в секцию «Скиллы — основной интерфейс» в `CLAUDE.md`, а если он пользовательский — в списки команд `README.md` и `README_ru.md` |
| Меняешь frontmatter (`name`, `description`) любого `SKILL.md` | `npm run gen:skills-list`. `name` обязан совпадать с именем каталога |
| `README.md`, `README_ru.md`, `INTEGRATION.md`, `CONTRIBUTING.md` или любой файл из `demoFiles` | `npm run gen:demo-manifest` — эти файлы закреплены по sha256 |
| Версия | Только через `node scripts/release.mjs`, не руками в одном файле (см. «Релиз») |

`skills/Skills list.md` и хэши в `demo-manifest.json` руками не правь, только генераторами. После любой правки из таблицы прогони `npm test` локально. Хук сделает это сам, если он включён, но если он выключен, падение увидишь уже в CI.

## Проверки

```bash
npm test
```

Проверяется: версия во всех манифестах и путь к скиллам в каждом, состав и frontmatter скиллов, актуальность `Skills list.md`, отсутствие плоского формата логов, guard приватности, целостность демо-манифеста (включая хэши маркированных блоков — не только целых файлов), отсутствие симлинков, согласованность `obsidian-plugins.json` с `community-plugins.json` и поведение хуков.

Guard приватности — не формальность: базовые скиллы приходят из личного vault автора, и он ловит забытые упоминания. Он ловит два класса: общие (абсолютные домашние пути пользователя под `/home`, `/Users` или `C:\Users`, и email-адреса — их код зашит в `tests/conventions.test.mjs`, приватных значений сам тест не называет) и проектно-специфичные (названия компаний, городов и т.п.) — их берёт из необязательного локального файла `.privacy-terms` (см. `.privacy-terms.example`), который в `.gitignore` и не приезжает при клоне. Заведи свой `.privacy-terms`, если у тебя есть свои термины для отлова.

## Прогон на чистом Obsidian

`npm test` проверяет согласованность файлов, но не то, что клон реально разворачивается. Рабочий vault для этого не годится: в нём плагины уже стоят (в каталоге разработки, например, лежит `omnisearch`, которого нет ни в `obsidian-plugins.json`, ни в `.obsidian/community-plugins.json`), `files/tasks.json` сгенерирован, vault подключён — половина шагов развёртывания там выполнена заранее и молча не сломается. Поэтому всё, что видит новый пользователь, проверяется только на свежем клоне в отдельной папке.

1. **Клон в одноразовый каталог.**

   ```bash
   git clone . /tmp/oaw-clean && cd /tmp/oaw-clean
   ```

   Локальный клон берёт текущую ветку **без незакоммиченного** — проверяй то, что собираешься пушить, а не то, что лежит в рабочем дереве. Клон с GitHub (`git clone https://github.com/popstas/obsidian-agent-workspace`) проверяет уже опубликованное — то, что получит пользователь.

2. **Плагины.**

   ```bash
   bash scripts/install-obsidian-plugins.sh
   ```

   Что смотреть:

   - в выводе есть строка на каждый плагин из `obsidian-plugins.json`, а `tasks-mover` пропущен как вендоренный;
   - `.obsidian/plugins/` содержит ровно те id, что перечислены в `.obsidian/community-plugins.json`, — ни лишних, ни недостающих;
   - `data.json` у `file-explorer-plus` и `obsidian-icon-folder` на месте: их настройки едут из git, и установщик не должен их затирать;
   - `git status` пуст — код чужих плагинов под `.gitignore`.

   Второй запуск подряд обязан быть идемпотентным: качается только отсутствующее или то, что ниже `minVersion`. Плагин, который перекачивается каждый раз, — признак недостижимого `minVersion` (см. заметку про `dataview` в `obsidian-plugins.json`).

3. **Генератор счётчика.**

   ```bash
   node .claude/gen-tasks-json.cjs && cat files/tasks.json
   ```

   `files/tasks.json` в `.gitignore`, в клоне его нет — он должен появиться с ненулевым `open`. На старте сессии агента то же самое делает хук `SessionStart`.

4. **Подключить клон как отдельный vault** (Open folder as vault), не переоткрывая рабочий. Что смотреть в самом Obsidian:

   - Settings → Community plugins: нет включённых, но отсутствующих плагинов и уведомлений о неудачной загрузке;
   - дерево файлов: `file-explorer-plus` прячет служебное (`AGENTS.md`, `CHANGELOG.md`, `CONTRIBUTING.md`, `INTEGRATION.md`, `scripts/`, `tests/`), у файлов лестницы стоят иконки от `obsidian-icon-folder`;
   - хоткеи из `.obsidian/hotkeys.json` подхватились;
   - `index.md` открывается, wikilinks в `tasks.md` ведут в существующие файлы, а не в «not created yet».

5. **Сессия агента в клоне.** Подсказка `SessionStart` появилась, скиллы видны (`/list-tasks`), маркетплейс из `.claude-plugin/` подключается. Здесь же — одноразовые и разрушающие сценарии, которые в рабочем vault не проверить: полный прогон `INTEGRATION.md` в режиме 1 и `demo-content-delete`, который удаляет демо-контент и самого себя.

6. **Уборка.** Удалить папку клона и **отвязать vault в Obsidian** — иначе он останется в списке хранилищ и в `obsidian://` deeplink. Проще всего убрать его из окна выбора хранилища; реестр лежит в `obsidian.json` рядом с userData (macOS — `~/Library/Application Support/obsidian/`, Windows — `%APPDATA%\obsidian\`, Linux — `~/.config/obsidian/`, у snap-сборки — `~/snap/obsidian/current/.config/obsidian/`) и появляется только после первой регистрации vault.

Тот же прогон на Windows проверяет вторую половину клиентских скриптов: `install-obsidian-plugins.ps1` под **Windows PowerShell 5.1**, а не `pwsh`, и русские сообщения установщика и хуков без мусора в консоли. Кодировочные инварианты (BOM у файла, `OutputEncoding` в потоке) тесты держат статически, но развалившийся на реальной консоли вывод виден только так.

## Инварианты, которые нельзя нарушать

- **`skills/` — единственный источник истины.** Каталога `.claude/skills` в репозитории нет: Obsidian скрывает dot-каталоги, и скиллы стали бы недоступны для чтения из vault.
- **Никаких симлинков.** На Windows git по умолчанию их не создаёт.
- **Клиентские скрипты не зовут `jq`, `python` и Node.** Целевой пользователь — не разработчик на чистой macOS или Windows: ничего из этого у него не установлено, а `jq` не ставится с ОС нигде. Всё, что запускает сам пользователь (установщик плагинов, хуки Codex), едет парой равноправных реализаций: `.sh` на bash + `curl` и `.ps1` на PowerShell. Вести себя они обязаны одинаково — паритет держат тесты в `tests/`, параметризованные по раннеру, а не сверкой глазами. Node остаётся ровно в одном месте на клиенте: хуки Claude Code (там нет поля `commandWindows`, одной строкой команды две ОС не покрыть — у Codex такое поле есть, и его хуки поэтому без Node). Всё, что нужно только разработке базы, — тесты, генераторы, changelog, release — по-прежнему `.mjs` на Node.
- **`.sh` — потолок bash 3.2 и утилиты BSD.** macOS везёт bash 3.2 (новее — лицензия) и BSD-утилиты вместо GNU. Нельзя: `declare -A`, `mapfile`/`readarray`, `${var,,}`/`${var^^}`, `**` в globs. У BSD-утилит другие правила: `mktemp` требует шаблон (`mktemp "${TMPDIR:-/tmp}/oab.XXXXXX"`, иначе на macOS пусто), у `sed -i` другой синтаксис, а `grep -P`, `date -d`, `readlink -f`, `sort -V` отсутствуют вовсе. Проверяй по `man` BSD, а не по тому, что прошло на Linux. Нога CI `macos-latest` гоняет тесты против системного `/bin/bash` явно (`OAB_BASH=/bin/bash`): в PATH раннера первым стоит Homebrew-bash 5.x, и голый `bash` проверял бы совсем не ту реализацию. Какой бинарник и какой версии реально исполнял `.sh`, видно в логе прогона — отдельным шагом и диагностикой теста «bash-раннер тестов».
- **`.ps1` — потолок Windows PowerShell 5.1.** На чистой Windows стоит именно он, `pwsh` 7+ там нет. Нельзя: `??`, `?.`, тернарный оператор, `ConvertFrom-Json -AsHashtable`. Прогон под `pwsh` ничего не доказывает — 5.1-специфичные баги он не воспроизводит, тесты гоняют через каждый найденный в PATH интерпретатор.
- **Каждый `.ps1` сохраняется в UTF-8 с BOM.** Без BOM Windows PowerShell 5.1 читает файл в системной ANSI-кодировке, а не в UTF-8: кириллица в строках и комментариях разваливается, и скрипт не парсится вообще — падает до первой строки выполнения. BOM здесь не мусор редактора, который можно «почистить»; это условие запуска, и его требует тест.
- **Каждый `.ps1` выставляет `[Console]::OutputEncoding = New-Object System.Text.UTF8Encoding $false`** до первого вывода. Иначе 5.1 пишет stdout и stderr в консольную OEM-кодировку (CP866 для русской локали) — русские сообщения превращаются в мусор, а приёмник хука получает синтаксически валидный JSON с испорченным содержимым, то есть тихую порчу вместо падения. `$false` обязателен: UTF-8 **без** BOM в потоке, BOM в потоке ломает разбор на приёмной стороне. Это не дубликат BOM файла — нужны обе вещи, и обе требует тест.
- **Никаких runtime-зависимостей из npm.** Тесты — только `node:test`.
- **Дневные логи вложенные**, отчёты плоские.

## Релиз

```bash
node scripts/release.mjs 0.3.0   # версия в пяти файлах
npm run changelog                 # CHANGELOG.md из conventional commits
git commit -am "chore(release): 0.3.0"
git tag -a v0.3.0 -m v0.3.0 && git push --follow-tags
```

**Тег обязан быть аннотированным** (`-a`): `--follow-tags` отправляет только аннотированные теги, а lightweight (`git tag v0.3.0`) молча останется локальным — push пройдёт успешно, но workflow не запустится и релиза не будет. Проверить, что тег доехал: `git ls-remote --tags origin`.

Тег запускает `.github/workflows/release.yml`, который создаёт GitHub Release. Репозиторий до-единичный: breaking changes едут минорным бампом с явной пометкой BREAKING в `CHANGELOG.md`.

`npm run changelog` перегенерирует `CHANGELOG.md` целиком из истории коммитов, а не дописывает к нему. Править файл руками бессмысленно — следующий релиз затрёт правку; развёрнутый текст для людей место в описании GitHub Release, а не в `CHANGELOG.md`.

## Что оставить пользователю

Меняя скиллы, помни, что они шаблоны: конкретные имена каталогов, людей и трекеров в них — примеры, которые адаптируются под пользователя по `INTEGRATION.md`. Не вписывай в них ничего своего.
